REPAIRS
Authentication and accounts:
- Renamed the email verification field to email_verified, avoiding the conflict
  with django-otp's is_verified() session-verification method.
- Both login URLs now use the same custom login view. Authentication requires an
  active account and verified email. Confirmed OTP devices determine whether a
  code is required, even if the old compatibility flag is stale.
- Authenticator setup uses a single view and valid templates. It marks the flag
  enabled only after device confirmation and synchronizes device changes.
- QR code output is exercised by the enrollment regression test.
- Successful OTP verification records the device through django-otp's login API.
- Pending OTP challenges expire after five minutes, have an attempt limit, and
  are invalidated when the account password changes.
- Existing authenticated sessions cannot skip a newly enrolled authenticator.
- IP request limits use atomic database updates shared by application workers.
  Login, OTP, recovery, registration, resend, settings, and reset email requests
  are rate limited.
- Verification links use their own purpose-specific token generator, become
  invalid after verification, and cannot be used as password-reset tokens.
- Email addresses are normalized and uniquely constrained without regard to
  case. Login accepts email capitalization differences.
- Registration rolls back and shows a useful error if mail delivery fails.
- Password reset is tested through completion and token reuse rejection; invalid
  links now display a clear error rather than an empty unusable form.
- Disabling 2FA, replacing recovery codes, and account deletion require the
  current password. Logout is a CSRF-protected POST action.
- Recovery code consumption is atomic and single-use. Only active, verified
  accounts can recover. New codes display once, and replacement invalidates old
  codes. Missing or invalid recovery encryption keys fail explicitly.
- Secret-bearing logging/printing and SQLite debugging queries were removed.

Vault and interface:
- Encryption keys are no longer stored in password rows. Runtime encryption uses
  the persistent key supplied by configuration. Legacy rows are re-encrypted in
  a transactional migration before the key column is removed.
- Dashboard passwords are absent from the initial HTML and fetched only on an
  authorized, CSRF-protected POST for Show/Copy.
- Password strings enter DOM input values, never innerHTML. HTML, quotes, and
  ampersands remain literal text. Password values are not logged in the console.
- Revealed passwords clear when hidden, after 30 seconds, or when the tab hides.
- Show/hide, copy, search, category filtering, generation, strength feedback,
  delete confirmation/cancellation, and error handling have DOM coverage.
- Deletes reload the dashboard after success so categories, counts, and entries
  remain consistent. Category deletion explicitly warns that it deletes entries.
- Ownership checks and CSRF protection remain in place and are tested.
- Bound forms display validation errors and preserve entered values where
  appropriate. Leading/trailing password whitespace is preserved through login,
  password changes, and vault storage. Generator output always includes lowercase
  plus each selected character class.
- Missing CSS/JavaScript assets were restored. Bootstrap is served locally,
  external font/CDN dependencies were removed, and a local favicon was added.
- Sensitive page responses carry no-store cache headers.

Runtime and setup:
- Runtime dependencies were updated and pinned, including Django 5.2.19,
  django-two-factor-auth 1.18.1, and current cryptography/django-otp packages.
- Production settings enable HTTPS redirects, secure cookies, HSTS, and explicit
  hostname/origin configuration. Trusted proxy headers require explicit opt-in.
- WhiteNoise serves collected static assets, including under Gunicorn.
- Added a setup script that creates persistent secrets only for a new install;
  existing .env contents and encryption keys were preserved.
- Added .gitignore, .env.example, development requirements, and SETUP.txt.
- Applied migrations to the local database and restricted .env/database file
  permissions. No demo users or administrator passwords were created.
- Local development server: http://127.0.0.1:8010/

HTTP intentionally differs from production HTTPS. The initial api/ directory
remains an unused scaffold; no new public API was added.
